Panduan Integrasi untuk Developer

Engine ini memeriksa kualitas foto POD/paket (buram, pecah, gelap, teks tidak terbaca), mengoptimasi dan mengompres ke < 1 MB tanpa memanipulasi isi gambar, dan menyediakan bukti pengiriman untuk penagihan. Engine tidak menyentuh status pengiriman: status tetap milik aplikasi pengiriman, engine hanya memberi keputusan allow_status_update. Halaman ini cukup untuk mulai integrasi. Detail lengkap ada di docs/integration-guide.md dan Swagger (bisa dicoba langsung).

Cara tercepat: kirim foto, terima keputusan (1 panggilan)

Engine memproses gambar; sebelum dan sesudahnya dikerjakan aplikasi pengiriman, termasuk menyimpan foto pengiriman ke bucket-nya. Aplikasi mengirim foto dari kurir langsung ke engine. Engine memeriksa dan mengoptimasi foto, lalu menjawab dengan keputusan dan foto hasil (output_image, base64, < 1 MB). Engine tidak menulis ke bucket aplikasi; engine hanya mengarsipkan salinannya sendiri di bucket ocr (per aplikasi, 520 hari) di belakang layar. Satu request, tunggu maks. 3 detik (urutan lengkap: kapan foto dikirim & divalidasi).

HasilYang dilakukan aplikasi pengiriman
allow_status_update: trueFoto diterima. Simpan output_image (decode base64) ke SILO dengan kode dan key Anda sendiri, update status pengiriman, tampilkan courier_message jika ada. optimized: false = foto asli sudah memenuhi syarat dan dikembalikan apa adanya.
allow_status_update: falseFoto ditolak (output_image: null). Jangan simpan, kirim balik courier_message ke kurir, jangan update status, kurir foto ulang.
Engine error / timeoutSimpan foto asli ke SILO seperti sekarang (kode lama tetap dipakai sebagai cadangan), lalu update status (fail-open).

Kirim juga object_key (key SILO yang akan Anda pakai) supaya Web UI, evidence, dan backup NAS bisa menampilkan fotonya (engine hanya membaca). Key baru diketahui setelah menyimpan? Laporkan dengan POST /v1/photos/{id}/stored (reportStored di client).

import base64
import requests

def check(path, awb, key):
    """Return (allow, courier_message, data_untuk_silo). Engine bermasalah -> (True, None, foto asli): fail-open."""
    original = open(path, "rb").read()
    try:
        r = requests.post("{{BASE}}/v1/analyze", params={"timeout_ms": 3000},
                          headers={"X-API-Key": PQE_API_KEY, "Accept-Language": "id"},
                          files={"file": ("foto.jpg", original, "image/jpeg")},
                          data={"awb": awb, "photo_type": "pod_recipient", "object_key": key}, timeout=(2, 8))
        p = r.json() if r.status_code == 200 else {}
    except requests.RequestException:
        p = {}  # fail-open
    allow = p.get("allow_status_update", True)
    out = p.get("output_image")
    data = base64.b64decode(out["base64"]) if out else (original if allow else None)
    return allow, p.get("courier_message"), data

Uji coba tanpa aplikasi

Sebelum menulis kode, coba dulu engine dari HP lewat halaman Uji Coba Kamera. Halaman itu berperan sebagai aplikasi kurir: ambil foto, kirim ke engine, lalu tampil persis pesan yang akan dilihat kurir beserta detail analisis (skor, alasan, perbaikan otomatis, ukuran sebelum/sesudah kompresi, waktu tunggu).

ModeYang terjadi
Simulasi aplikasi kurirSama dengan integrasi level 2: POST /v1/analyze?timeout_ms=3000 dengan file + metadata. Hasil analisis tercatat (tenant uji-coba, retensi 30 hari) dan fotonya diarsipkan engine di ocr/uji-coba/..., jadi bisa dibuka di Web UI dan evidence (di aplikasi asli, aplikasi juga menyimpan foto hasil ke bucket-nya).
Uji cepatPOST /v1/analyze/preview: hanya dianalisis, tidak disimpan.

Buka dari HP di jaringan yang sama: http://<IP-PC-engine>:8000/ui/coba.html. Tombol Ambil foto membuka kamera bawaan HP (seperti aplikasi kurir). Kamera langsung di browser butuh HTTPS; jalankan PQE_HTTPS_HOST=<IP-PC> docker compose -f docker-compose.yml -f docker-compose.https.yml up -d lalu buka https://<IP-PC>:8443/ui/coba.html. Opsi Tampilkan sebagai mode memperlihatkan pengalaman kurir di mode shadow/warn/enforce tanpa mengubah config.

Diagram alur

Kapan foto dikirim ke engine, dan kapan divalidasi?

UrutanSiapaApa yang terjadi
1KurirAmbil foto POD, tekan Kirim di aplikasi.
2 · kirimAplikasi pengiriman → engineFoto langsung dikirim ke engine (belum ke SILO, status belum diupdate): POST /v1/analyze dengan file foto (+ object_key opsional). Satu request, tunggu maks. 3 detik.
3 · scanEngineValidasi gambar (biasanya 0,2–2 detik): ketajaman, pecah, resolusi, cahaya, EXIF, duplikat, OCR → verdict.
4a · diterimaEngine → aplikasiOptimasi + kompres < 1 MB (tanpa manipulasi). Engine menjawab allow_status_update: true + output_image (foto hasil, base64). Setelah menjawab, engine mengarsipkan foto hasil yang sama di bucket ocr.
4b · ditolakEngine → aplikasi → kurirTanpa foto hasil (output_image: null). Engine menjawab allow_status_update: false + courier_message, aplikasi mengirim balik pesan itu ke kurir untuk foto ulang (kembali ke 1). Engine mengarsipkan foto asli di ocr untuk review ops.
5 · simpanAplikasi pengiriman → SILODiterima → aplikasi menyimpan output_image ke bucket-nya + update status. Ditolak → aplikasi tidak menyimpan, status tidak diupdate. Engine tidak menjawab dalam 3 detik → aplikasi menyimpan foto asli (kode lama) + update status (fail-open).

Engine hanya membaca bucket aplikasi dan menulis ke bucket arsipnya sendiri (ocr, per aplikasi, masa simpan 520 hari): foto diterima = foto hasil, foto ditolak = foto asli (untuk review & kalibrasi). Web UI, evidence, dan backup NAS memakai arsip ini. Menyimpan foto asli di bucket aplikasi (selain versi optimasi) adalah keputusan aplikasi. Level 0/1 (aplikasi tidak memanggil engine): aplikasi menyimpan ke SILO sendiri, engine membaca dan memeriksa belakangan lewat bucket notification/polling; hasilnya untuk laporan dan evidence, tetapi tidak bisa menahan status.

A. Alur integrasi sampai go-live

Mode dinaikkan admin lewat Web UI (menu Tenant) tanpa mengubah aplikasi. Selama shadow kurir tidak melihat apa pun; data dipakai untuk kalibrasi threshold.

B. Alur penggunaan saat aplikasi berjalan (level 2)

Garis putus-putus = balasan. Foto masuk engine dulu; jika diterima, aplikasi menyimpan foto hasil engine ke SILO. Status pengiriman ada di aplikasi pengiriman; engine hanya memberi keputusan dan foto hasil. Engine mati/lambat → aplikasi menyimpan foto asli dan status tetap diupdate (fail-open).

C. Keputusan di aplikasi pengiriman

Cukup baca allow_status_update, courier_message, dan output_image. Nilainya mengikuti mode yang diatur admin (false hanya di mode enforce), jadi kode aplikasi tidak berubah saat mode dinaikkan.

D. Proses di dalam engine

Semua jalur masuk berakhir di antrean yang sama (idempotent: foto yang sama tidak diproses dua kali). Engine tidak memanipulasi isi gambar: hanya optimasi ukuran dan kompresi. Engine hanya membaca bucket aplikasi; foto upload diarsipkan di bucket ocr setelah respons.

1. Aturan emas

Status pengiriman milik aplikasi pengiriman. Engine tidak pernah mengubah status; engine hanya menjawab allow_status_update. Jika false (foto ditolak), jangan update status sampai kurir mengirim foto ulang yang diterima.
Engine bermasalah tidak boleh menahan kurir. Timeout ≤ 3 detik. Jika engine lambat/mati/error, anggap allow_status_update: true (fail-open) dan lanjutkan proses seperti biasa.
API key hanya di server. Jangan menaruh API key di aplikasi Android/iOS/Flutter atau JavaScript browser. Aplikasi mobile memanggil backend Anda, backend memanggil engine.
Kirim foto asli dari kamera. Jangan kompres/resize di aplikasi (contoh imageQuality/maxWidth kecil di Flutter). Engine yang mengompres dengan aman.
Runtime wajib versi yang sudah di-patch (security release 21 Okt 2026): Node.js ≥ 22.23.4 / 24.22.1 / 26.12.1, PHP ≥ 8.2.35 / 8.3.36 / 8.4.27 / 8.5.12.

2. Pilih cara integrasi

LevelYang dikerjakan aplikasiHasil

Minta ke admin engine: kode tenant (satu per aplikasi) dan API key role app. Simpan key di env server (PQE_API_KEY). Cek key:

{
  "id": "e350b8bd...", "status": "done",

  "action": "reject",             // log | notify | reject (sesuai mode yang diatur admin)
  "reasons": [{ "code": "BLURRY", "severity": "reject", "message": "Foto buram",
                "suggestion": "Pegang HP dengan stabil, ketuk layar untuk fokus, lalu foto ulang." }],
  "output_image": null,           // hanya dari upload file. Diterima: {"content_type","bytes","optimized","sha256","base64"}; ditolak: null
  "object": null,                 // lokasi foto di bucket aplikasi (dari object_key / reportStored); null = tidak disimpan aplikasi
  "archive": null,                // salinan engine di bucket ocr (ditulis beberapa detik setelah respons; terlihat di GET /v1/photos/{id})
  "evidence_eligible": false      // apakah foto masuk bukti penagihan pelanggan
}
FieldArti
allow_status_updatePaling penting. false hanya jika foto ditolak (REJECT di mode enforce, atau ops meminta foto ulang): aplikasi pengiriman tidak boleh update status. Selain itu true.
courier_messageKalimat siap tampil untuk kurir, atau null jika kurir tidak perlu melihat apa pun (PASS / mode shadow).
output_imageFoto yang disimpan aplikasi ke SILO (decode base64): versi optimasi < 1 MB, atau foto asli apa adanya jika sudah memenuhi syarat (optimized: false). null jika foto ditolak, atau engine belum selesai (202, simpan foto asli). Salinannya juga diarsipkan engine di bucket ocr.
objectLokasi foto di bucket aplikasi (bucket, key) dari object_key atau POST /v1/photos/{id}/stored; opsional, pelengkap arsip engine (hanya dibaca).
archiveSalinan engine di bucket arsip (ocr, <tenant>/<yyyy>/<mm>/<dd>/<id>): foto hasil (diterima) atau foto asli (ditolak). Dipakai Web UI, evidence, dan backup NAS; dihapus setelah 520 hari.
retake_requiredtrue = kualitas tidak memenuhi syarat (buram berat, pecah, terlalu kecil, terlalu gelap). Di mode warn kurir hanya diberi tahu; di mode enforce status ditahan.
verdictPASS layak, WARN kurang ideal tapi masih terbaca (tetap diterima & masuk evidence), REJECT tidak layak.
reasons[].codeKode stabil untuk logika aplikasi. message/suggestion sudah diterjemahkan (header Accept-Language: id|en).
reasons[].severityinfo hanya informasi (contoh EXIF_MISSING), jangan ditampilkan sebagai kesalahan.

KondisiYang ditampilkan aplikasi

import hashlib, hmac, time

def verify(secret: str, ts: str, raw_body: bytes, signature: str) -> bool:
    if not ts or abs(time.time() - int(ts)) > 300:
        return False
    mac = hmac.new(secret.encode(), ts.encode() + b"." + raw_body, hashlib.sha256).hexdigest()
    return hmac.compare_digest(f"sha256={mac}", signature or "")

10. Optimasi tanpa manipulasi

Engine tidak memanipulasi isi gambar: tidak ada AI, filter, penajaman, crop, atau koreksi warna/cahaya. Yang dilakukan hanya optimasi dan kompresi dinamis, sehingga keabsahan dokumen terjaga.
  • Foto kecil tidak disentuh (sudah di bawah target dan ukuran wajar): dikembalikan apa adanya (output_image.optimized: false).
  • Foto besar: diperkecil proporsional bila perlu, lalu dicari kualitas JPEG tertinggi yang muat < 1 MB. Pengaman SSIM memastikan teks tetap terbaca; jika target tidak tercapai tanpa merusak keterbacaan, keterbacaan diutamakan.
  • Rotasi mengikuti orientasi kamera (EXIF) agar foto tidak miring saat ditampilkan.
  • Foto hasil dikembalikan di output_image, aplikasi yang menyimpannya ke bucket-nya. Engine menyimpan salinannya hanya di arsipnya (ocr). Kode verifikasi keaslian (SHA-256) merujuk ke foto asli yang dikirim; output_image.sha256 adalah hash foto hasil.
  • Foto yang kualitasnya tidak memenuhi syarat (buram, pecah, terlalu kecil, terlalu gelap/terang) tidak "dibenarkan": engine mengembalikan retake_required: true dan kurir diminta foto ulang.

Koreksi pencahayaan dengan kurva global terverifikasi tersedia sebagai opsi per profile (enhance.enabled: true), nonaktif secara bawaan.

12. Checklist sebelum go-live

  • ☐ Update status kurir tetap jalan saat engine dimatikan (uji!)
  • ☐ Semua panggilan punya timeout (≤ 3 dtk) dan fail-open (engine tidak menjawab → simpan foto asli)
  • ☐ Foto diterima: simpan output_image ke bucket aplikasi; foto ditolak: tidak disimpan aplikasi, status tidak diupdate
  • ☐ API key hanya di env server, tidak di aplikasi mobile/browser/git
  • ☐ Foto dikirim asli dari kamera (tanpa kompres di aplikasi)
  • ☐ Metadata awb, photo-type, courier-id, customer-id terkirim
  • ☐ allow_status_update: false → status pengiriman tidak diupdate, kurir diminta foto ulang (uji dengan foto buram di mode enforce, bisa lewat halaman Uji Coba)
  • ☐ courier_message ditampilkan apa adanya ke kurir saat tidak null
  • ☐ Webhook: tanda tangan diverifikasi, balas 2xx cepat, idempotent
